# ComInspect — Phase 1: Research & Architecture

ComInspect is a serial-port inventory and identity manager. It answers one question within
seconds of opening:

> **"What are all these COM ports, and what does each one belong to?"**

The central design principle is:

```
Persistent device identity  ──►  current OS port assignment
"FTDX10 CAT Enhanced"            COM7 (previously COM5), connected, CAT verified
```

A COM number is *never* treated as the identity of a device. It is an attribute of the device
that the operating system assigned, and which can change.

This document covers the eleven Phase 1 deliverables. Each section describes the implementation
that ships in this repository and marks any part that is deferred.

## 1. Recommended technology stack

### Candidates evaluated

| Approach | Installer size | Idle RAM | Cold start | Low-level OS access | Built-in secure updater | Verdict |
|---|---|---|---|---|---|---|
| **Rust + Tauri 2** (system WebView) | ~3–8 MB | ~30–80 MB | < 1 s | Direct FFI from Rust to CfgMgr32/SetupAPI, IOKit, sysfs/netlink; no marshalling layer | **Yes**: `tauri-plugin-updater` with mandatory Ed25519/minisign signatures, GitHub Releases static feed, generated by `tauri-action` | **Chosen** |
| .NET 8 + Avalonia | 25–70 MB self-contained | 60–120 MB | 1–2 s (better with AOT) | Good P/Invoke on Windows; IOKit/libudev via P/Invoke is manual | Via Velopack (third-party, good) | Strong runner-up |
| Python + PySide6 (Qt) | 40–90 MB (PyInstaller) | 80–150 MB | 1–3 s | ctypes works but is fragile; hard to type-check | None maintained; would need a custom or TUF-based updater | Rejected: size, startup, packaging |
| Flutter desktop | 20–35 MB | 80–150 MB | ~1 s | `dart:ffi` is workable but awkward for SetupAPI/IOKit | Community plugins wrapping Sparkle/WinSparkle | Rejected: FFI ergonomics, updater maturity |
| Qt/C++ native | 20–40 MB | 30–60 MB | < 1 s | Excellent | None (Qt Installer Framework is heavy) | Rejected: development/packaging cost |
| Electron | 80–150 MB | 150–300 MB | 1–2 s | Needs native Node addons for SetupAPI/IOKit | electron-updater | Excluded, per requirements |

### Decision: Rust + Tauri 2 + Svelte 5

* **Low resource use / small installer / fast startup.** Tauri uses the operating system's
  WebView (WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux), so the bundle contains
  only our Rust binary and a few hundred KB of compiled UI. Svelte compiles away to plain
  JavaScript with no virtual-DOM runtime.
* **Reliable low-level metadata.** All device discovery is written in Rust against the native
  APIs (`windows-sys` for CfgMgr32/msports/registry, `io-kit-sys` + `core-foundation` for IOKit,
  direct sysfs/netlink on Linux). The same language covers the UI backend, so no IPC or helper
  process is needed.
* **Updates are first-class.** Tauri's updater plugin requires every update to be signed.
  `tauri-action` builds all platforms in GitHub Actions and publishes a `latest.json` feed that
  installed apps poll. See [§9](#9-update-and-release-architecture).
* **Packaging.** Tauri's bundler produces NSIS (`-setup.exe`) and MSI installers on Windows,
  `.app`/`.dmg` on macOS, and AppImage, `.deb` and `.rpm` on Linux, from one config file.
* **Maintainability.** Strict Rust types serialize straight to TypeScript types used by the UI,
  and platform code is isolated behind one small interface.

Supporting libraries:

| Concern | Library | Why |
|---|---|---|
| Database | `rusqlite` (bundled SQLite) | Transactional, crash-safe, zero-install, easy versioned migrations |
| Serial I/O (diagnostics only) | `serialport` 4.x (no libudev) | Mature, cross-platform, exposes modem lines (CTS/DSR/DCD/RI) and DTR/RTS |
| Windows FFI | `windows-sys` | Official Microsoft bindings, zero-cost |
| macOS FFI | `io-kit-sys`, `core-foundation` | Same bindings the `serialport` crate uses |
| UI | Svelte 5 + Vite + TypeScript | Small bundles, readable components |
| Logging | `tauri-plugin-log` | Rotating log file in the OS log directory |

## 2. Cross-platform architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│ UI (Svelte, ui/)                                                         │
│  Table · filters · search · inspector · diagnostics · About/Updates      │
└───────────────▲──────────────────────────────┬───────────────────────────┘
      events    │ inventory-updated,           │ invoke(command)
                │ inventory-events             ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ App shell (Rust, src-tauri/)                                             │
│  commands · monitoring loop · updater · settings · logging · launch      │
│  confirmation · export/import file dialogs                               │
└───────▲───────────────────────▲───────────────────────────▲──────────────┘
        │                       │                           │
┌───────┴────────────┐ ┌────────┴────────────────┐ ┌────────┴──────────────┐
│ cominspect-platform│ │ cominspect-store        │ │ cominspect-core       │
│ Platform adapters  │ │ Device database         │ │ Pure logic, no I/O    │
│  windows/ linux/   │ │  SQLite + migrations    │ │  model (DiscoveredPort│
│  macos/            │ │  + backups              │ │  ScanResult)          │
│ Monitoring service │ │  Inventory service:     │ │  identity engine      │
│  (change hints)    │ │  reconcile scans →      │ │  known-device hints   │
│ Diagnostics        │ │  history, events, view  │ │  conflict analysis    │
│  (explicit only)   │ │  export / import        │ │  export format        │
└────────────────────┘ └─────────────────────────┘ └───────────────────────┘
        ▲ produces core::ScanResult      ▲ uses core::identity for matching
```

Rules that keep the layers clean:

* **`cominspect-core`** has no OS or database dependencies. It defines the normalized
  `DiscoveredPort` model that every adapter produces, the identity engine, the known-device hint
  database, and conflict analysis. Everything in it is unit-tested on every OS.
* **`cominspect-platform`** is the only crate with `#[cfg(target_os)]` code. Each adapter has two
  halves:
  * *collection* reads raw OS data (FFI, sysfs);
  * *interpretation* turns raw records into `DiscoveredPort`.

  Interpretation is written as pure functions, so it is tested with recorded fixtures on any OS.
  This matters because Windows and macOS logic cannot be exercised on a Linux developer machine.
* **`cominspect-store`** owns persistence and reconciliation. It turns a `ScanResult` into device
  history, arrival/removal/renumbering events, and the view model the UI renders.
* **The UI never talks to the OS.** It only calls typed commands and receives events. It has no
  file-system or shell permissions: export/import dialogs run in Rust.
* **`cominspect-cli`** reuses the same crates for headless diagnostics:
  `cominspect-cli list --json`. CI runs it on real Windows, macOS and Linux runners.

### Monitoring service

```
 OS change hint ─┐          ┌── debounce 400 ms ──► scan (platform::discover)
 fallback poll  ─┼─► channel┤                        │
 manual refresh ─┘          └────────────────────────▼
                                    Inventory::reconcile(scan)
                                    ├─ identity matching
                                    ├─ history/events → SQLite
                                    └─ emit "inventory-updated" / "inventory-events"
```

| OS | Primary change hint | Fallback poll |
|---|---|---|
| Windows | `CM_Register_Notification` (device-interface arrival/removal, all classes) + `RegNotifyChangeKeyValue` on `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM` (catches non-PnP virtual ports) | 30 s |
| Linux | `NETLINK_KOBJECT_UEVENT` socket, filtered to `tty`/`usb`/`bluetooth` subsystems | 15 s |
| macOS | Cheap poll of `/dev/cu.*` every 1.5 s, followed by a full IOKit scan on change | 30 s full scan |

## 3. Windows serial-device enumeration strategy

### How Windows represents serial ports

* A serial port is a **device node (devnode)**, usually in the **Ports** setup class
  `{4D36E978-E325-11CE-BFC1-08002BE10318}`. Modems use the **Modem** class
  `{4D36E96D-…}`, and some virtual-port drivers use their own class. com0com, for example,
  uses `CNCPorts`.
* The **COM name** is stored by the port's driver in the devnode's *hardware key*
  (`Device Parameters`) as the `PortName` value. It is also embedded in the friendly name,
  e.g. `Silicon Labs Dual CP2105 USB to UART Bridge: Enhanced COM Port (COM7)`.
* Windows keeps devnodes for **devices that are no longer attached** ("non-present" or
  "phantom" devices). This is what Device Manager's *View → Show hidden devices* reveals, and why
  COM numbers accumulate.
* COM numbers are arbitrated by the **COM Name Arbiter database** (ComDB). This is a bitmap of
  reserved numbers. A phantom device keeps its number reserved, so new devices get
  ever-higher numbers.
* Active serial devices publish a mapping from kernel device name to COM name in the volatile key
  `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM`, e.g. `\Device\Silabser0 = COM7`. This is the "serial
  device map" that the Win32 serial stack and `.NET SerialPort.GetPortNames()` read. It also
  lists **non-Plug-and-Play virtual ports**, such as those created by some virtual-port tools,
  which have no devnode at all.
* USB serial devices hang under a USB devnode. For a **composite** device (e.g. CP2105 dual UART)
  the chain is `USB\VID_10C4&PID_EA70\<serial>` → `USB\VID_10C4&PID_EA70&MI_00\…` → port.
  For **FTDI** the port devnode lives on FTDI's own bus: `FTDIBUS\VID_0403+PID_6001+A10XYZ12A\0000`,
  where `A10XYZ12` is the USB serial number and `A` is the channel.
* **Bluetooth SPP** ports are devnodes like
  `BTHENUM\{00001101-0000-1000-8000-00805F9B34FB}_LOCALMFG&0002\7&…&0&001122334455_C00000000`.
  The 12 hex digits before `_C` are the remote device's address; `000000000000` marks an
  *incoming* (server) port. The paired device's name lives on the sibling devnode
  `BTHENUM\DEV_001122334455\…`.

### APIs used

Everything goes through documented, supported APIs. The implementation is in
`crates/cominspect-platform/src/windows/`.

| Purpose | API |
|---|---|
| Devices in the Ports / Modem classes, **including non-present devices** | `CM_Get_Device_ID_ListW` with `CM_GETIDLIST_FILTER_CLASS` (without `FILTER_PRESENT`) |
| Devices exposing `GUID_DEVINTERFACE_COMPORT` in any class (e.g. vendor classes) | `CM_Get_Device_Interface_ListW(…, CM_GET_DEVICE_INTERFACE_LIST_ALL_DEVICES)` + `CM_Get_Device_Interface_PropertyW(DEVPKEY_Device_InstanceId)` |
| Handle for present *or phantom* devnodes | `CM_Locate_DevNodeW(…, CM_LOCATE_DEVNODE_PHANTOM)` |
| Device properties | `CM_Get_DevNode_PropertyW` with `DEVPKEY_*` keys (see below) |
| `PortName` | `CM_Open_DevNode_Key(…, CM_REGISTRY_HARDWARE)` + `RegQueryValueExW("PortName")`; falls back to parsing `(COMn)` from the friendly name |
| Present? Problem code? | `DEVPKEY_Device_IsPresent`, `CM_Get_DevNode_Status` (`DN_HAS_PROBLEM`, `CM_PROB_*`) |
| Parent chain (USB device, hub location) | `CM_Get_Parent` + `CM_Get_Device_IDW`, falling back to `DEVPKEY_Device_Parent` |
| Active serial device map (incl. non-PnP virtual ports) | `RegOpenKeyExW(HKLM\HARDWARE\DEVICEMAP\SERIALCOMM, KEY_READ)` + `RegEnumValueW` |
| Reserved COM numbers | `ComDBOpen` + `ComDBGetCurrentPortUsage(CDB_REPORT_BITS)` from `msports.dll`. Some Windows configurations restrict `ComDBOpen` to administrators; if it is denied, the app falls back to a **read-only** read of the `ComDB` value under `HKLM\SYSTEM\CurrentControlSet\Control\COM Name Arbiter` and labels the data source in the UI. |
| Bluetooth device names | `CM_Get_Device_ID_ListW` with `CM_GETIDLIST_FILTER_ENUMERATOR` = `BTHENUM`, mapping `DEV_<address>` devnodes to friendly names |
| Change notification | `CM_Register_Notification` (callback, no window needed) + `RegNotifyChangeKeyValue` on SERIALCOMM |

**Alternatives considered and rejected**

* **WMI** (`Win32_SerialPort`, `Win32_PnPEntity`) is slow (hundreds of ms to seconds), needs
  COM initialization, misses many USB serial ports, and never reports non-present devices.
* **Walking `HKLM\SYSTEM\CurrentControlSet\Enum` directly** has an undocumented layout and
  fragile permissions. Registry reads are limited to the two documented locations above
  (SERIALCOMM and the ComDB fallback) plus the devnode hardware key opened through CfgMgr32.
* **SetupAPI** (`SetupDiGetClassDevs` without `DIGCF_PRESENT`) is equivalent: it is layered on
  CfgMgr32 and exposes the same `DEVPKEY` properties. CfgMgr32 is used directly because it is
  lighter and handles phantom devnodes explicitly.

### Information collected on Windows

| Field | Source | Stability / notes |
|---|---|---|
| Port name (`COM7`) | `PortName` in the devnode hardware key | User-changeable; persists per device instance. **Not an identity.** |
| Friendly name | `DEVPKEY_Device_FriendlyName` | Contains `(COMn)` |
| Device description | `DEVPKEY_Device_DeviceDesc` | From the driver INF, e.g. "…Enhanced COM Port" |
| USB product string | `DEVPKEY_Device_BusReportedDeviceDesc` on the USB devnode | iProduct as reported by the device |
| Manufacturer | `DEVPKEY_Device_Manufacturer` | From the INF |
| VID / PID / revision / interface | Hardware IDs and instance IDs (`VID_`, `PID_`, `REV_`, `MI_`), FTDIBUS `+` syntax | Stable per model |
| USB serial number | Unique-ID segment of the USB devnode's instance ID, if device-provided (no `&`) | Stable per unit **if the vendor programmed a unique serial** |
| Device instance ID | `CM_Get_Device_IDW` | Device-derived (strong) or, for devices without a serial, location-derived (`5&2a3b…&0&3`) |
| Hardware / compatible IDs | `DEVPKEY_Device_HardwareIds`, `DEVPKEY_Device_CompatibleIds` | |
| Location path / USB topology | `DEVPKEY_Device_LocationPaths` (e.g. `PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(2)#USB(3)`), `DEVPKEY_Device_LocationInfo` (`Port_#0003.Hub_#0002`) | Stable per physical USB socket |
| Container ID | `DEVPKEY_Device_ContainerId` | Groups all devnodes of one physical device |
| Driver service, provider, version, date, INF | `DEVPKEY_Device_Service`, `DriverProvider`, `DriverVersion`, `DriverDate`, `DriverInfPath` | Changes with driver updates |
| Enumerator / class | `DEVPKEY_Device_EnumeratorName`, `DEVPKEY_Device_Class`, `ClassGuid` | Used to classify USB / Bluetooth / virtual / PCI / built-in |
| Kernel device name | SERIALCOMM value name (`\Device\Silabser0`, `\Device\VCP0`, `\Device\BthModem0`, `\Device\com0com10` …) | Identifies the driver family; used to classify virtual providers |
| Connected? | `DEVPKEY_Device_IsPresent` / `CM_Get_DevNode_Status` | Runtime |
| Problem | `CM_Get_DevNode_Status` problem code | e.g. Code 10 on counterfeit/phased-out Prolific chips, Code 28 no driver |
| OS history | `DEVPKEY_Device_FirstInstallDate`, `InstallDate`, `LastArrivalDate`, `LastRemovalDate` | Lets the app show "last seen" for ports it has never seen itself |
| Bluetooth identity | BTHENUM instance ID → address, direction; `BTHENUM\DEV_<addr>` → name | |
| Virtual-port provider | Enumerator (`ROOT`, `COM0COM`, …), kernel device name, INF provider | Heuristic, labelled as such |
| Reserved COM numbers | ComDB | Includes stale reservations |

### Classification rules (Windows)

Classification follows the devnode ancestry for present devices and the enumerator for phantoms.

| Evidence | Classified as |
|---|---|
| An ancestor `USB\…` or enumerator `FTDIBUS`/`USB` | USB |
| Enumerator `BTHENUM`, or kernel name `\Device\BthModem*` | Bluetooth |
| Ancestor `PCI\…` (add-in cards, Intel AMT SOL) | PCI |
| `ACPI\PNP0501` and similar | Built-in (motherboard UART) |
| Root-enumerated (`ROOT\…`) or software bus (`COM0COM\…`), or present only in SERIALCOMM with no devnode | Virtual, with the provider taken from the kernel device name / INF |
| None of the above | Unknown |

## 4. Linux strategy

Linux has no equivalent of Windows' hidden devices: when a device is unplugged its tty
disappears. History of absent devices therefore comes from ComInspect's own database. The
implementation is in `crates/cominspect-platform/src/linux/`.

**Enumeration** walks `/sys/class/tty/*`:

* Entries with a `device` link are hardware- or driver-backed. The link's `subsystem` and `driver`
  identify the port type: `usb-serial` (`ftdi_sio`, `cp210x`, `pl2303`, `ch341`), `usb`
  (`cdc_acm` → `ttyACM*`), `pnp`/`platform`/`serial-base` (8250 UARTs), `pci`, `amba`
  (`ttyAMA*` on Raspberry Pi).
* Legacy `ttyS*` placeholders with no hardware (`type` = 0) are skipped.
* Virtual ttys without a device link are included only for serial-relevant names: `rfcomm*`
  (Bluetooth RFCOMM, with the kernel's `address` and `channel` attributes) and `tnt*`
  (tty0tty null-modem pairs).
* For USB ports the adapter walks up sysfs to the interface directory (`bInterfaceNumber`,
  `interface`) and the USB device directory (`idVendor`, `idProduct`, `serial`, `manufacturer`,
  `product`, `bcdDevice`, `busnum`, `devpath`). The **USB location** is expressed as
  controller + port chain (`pci-0000:00:14.0-usb-0:1.4`), which, unlike bus numbers, is stable
  across reboots. This matches udev's `by-path` scheme.
* `/dev/serial/by-id/*` and `/dev/serial/by-path/*` symlinks are mapped back to their ports and
  shown as persistent aliases. Users of Hamlib, Direwolf and similar tools on Linux often
  configure these by-id paths.
* **Permissions.** The adapter checks read/write access to the device node and reports the
  owning group (typically `dialout` or `uucp`), because "permission denied" is the most common
  Linux serial problem.

**Monitoring** uses a `NETLINK_KOBJECT_UEVENT` socket. Unprivileged processes may listen to
kernel uevents, so no udev library or daemon is required. A 15-second poll is kept as a safety
net.

**Stable identifiers:** USB serial number + VID/PID + interface. Without a serial, the USB
location. For on-board UARTs, the sysfs device path (e.g. `/sys/devices/pnp0/00:00`).

## 5. macOS strategy

The implementation is in `crates/cominspect-platform/src/macos/`.

* **Enumeration** uses IOKit: `IOServiceGetMatchingServices(IOServiceMatching("IOSerialBSDClient"))`.
  For each service it reads `IOCalloutDevice` (`/dev/cu.*`, the port applications should use),
  `IODialinDevice` (`/dev/tty.*`), `IOTTYBaseName`, and `IOTTYSuffix`.
* **USB metadata** is found with `IORegistryEntrySearchCFProperty(…, kIORegistryIterateRecursively
  | kIORegistryIterateParents)` for `idVendor`, `idProduct`, `USB Serial Number`,
  `USB Vendor Name`, `USB Product Name`, `locationID` (a 32-bit topology code, stable per
  physical port), `bInterfaceNumber` and `bcdDevice`.
* **Driver identity** comes from the IOKit class names of the parent chain: `AppleUSBFTDI`,
  `AppleUSBACMData`, `AppleUSBCHCOM`, Silicon Labs DriverKit extensions, and so on.
* **Bluetooth ports** (`cu.Bluetooth-Incoming-Port`, paired SPP devices) are recognized from their
  IOKit ancestry and names. macOS system ports (`debug-console`, `wlan-debug`) are classified as
  built-in and flagged as system ports.
* **Monitoring:** v1 polls the `/dev/cu.*` name list every 1.5 s, which is cheap, and runs a full
  IOKit scan when it changes. IOKit matching notifications (`IOServiceAddMatchingNotification`)
  are a planned enhancement.
* **Absent devices** are not remembered by macOS; history comes from the ComInspect database.

## 6. Persistent device fingerprinting strategy

### Identity keys

Every discovered port yields a set of **identity keys** with a *strength*. The engine lives in
`crates/cominspect-core/src/identity.rs`.

| Kind | Canonical value | Strength | Windows | Linux | macOS | Portable to another PC |
|---|---|---|---|---|---|---|
| `usb-serial` | `VID:PID:SERIAL:ifN` (hex upper-case; serial upper-cased, whitespace→`_`) | 100 | USB devnode instance ID / FTDIBUS | sysfs `serial` | `USB Serial Number` | **yes** |
| `bluetooth` | `AA:BB:CC:DD:EE:FF` (+ service/channel) | 95 | BTHENUM instance ID | rfcomm `address` | — | **yes** |
| `os-device` (device-derived) | OS instance ID with a device-provided unique part | 90 | instance ID | — | — | no |
| `os-device` (stable hardware/software) | on-board / PCI / virtual-driver instance | 80 | `ACPI\PNP0501\1`, `COM0COM\PORT\CNCA0` | sysfs path of on-board UART | — | no |
| `os-device` (location-derived) | OS instance ID generated from topology | 70 | `USB\VID_1A86&PID_7523\5&…&3` | — | — | no |
| `usb-path` | `VID:PID@LOCATION:ifN` | 60 | `LocationPaths` of USB devnode | controller + port chain | `locationID` | no |
| `virtual` | `provider:PORTNAME` | 50 | kernel device / enumerator | tty0tty name | — | yes (weak) |
| *(port name)* | `COM7` | 10 | fallback only, never stored as a key | | | |

Interface numbers make multi-port devices distinct: CP2105 interface 0 is the *Enhanced* port and
interface 1 the *Standard* port. FTDI channel letters A/B/C/D map to interfaces 0/1/2/3. The
canonical form is identical on all three operating systems, so an exported identity for
`10C4:EA70:<serial>:if0` matches the same radio port on another computer.

### Serial-number hygiene

A USB serial number is only used as a strong key when it is plausibly unique:

* Serials the OS generated are rejected. On Windows, instance IDs containing `&` are location-based.
* A block-list of well-known non-unique serials is rejected: `0001` (Silicon Labs default),
  `0000`, `A50285BI` (a common counterfeit FTDI serial), `1234567890`, and similar. Degenerate
  patterns are also rejected: one repeated character, or fewer than three characters.
* If two ports that are present at the same time share the same `usb-serial` key, that key is
  treated as non-unique **for that scan**. Both ports then fall back to weaker keys, and the UI
  warns the user.

### Matching algorithm

1. **Candidate edges.** For each discovered port and each of its keys, look up known devices
   sharing that key. The port-name fallback applies only to devices with no stronger evidence
   and the same transport.
2. **Conflict veto.** An edge is discarded if stronger evidence disagrees: different
   VID/PID, different raw serial numbers (or one side has a serial and the other doesn't),
   different interface numbers, different Bluetooth addresses, or different transport.
   For example, an FTDI cable with serial `ABC` that shows up in the USB socket where cable
   `XYZ` used to be is not merged with it.
3. **One-to-one assignment.** Edges are sorted by strength, then by recency, and assigned
   greedily so that a device can match at most one port per scan.
4. **Unmatched ports** become new device records.
5. **Learning.** Keys newly observed on a matched device are added to it. For example, the same
   serial-numbered cable in a new USB socket gains an extra `usb-path` key. Keys are never
   removed automatically.
6. **User merge.** Devices without unique serials (CH340, PL2303, many programming cables) are
   recognized by USB socket. When such a device moves to another socket, the user can link the
   new record with **Same device as…**. The merge unions keys, history and user fields, so
   both sockets are recognized from then on.

The inspector always shows *how* a device was recognized, for example "Recognized by USB serial
number" or "Recognized by USB port location (this device has no unique serial number)". This
tells the user how much to trust the match.

## 7. Database schema

SQLite, stored in the OS per-user application data directory, which updates never touch:

| OS | Location |
|---|---|
| Windows | `%LOCALAPPDATA%\io.github.kk4oda.cominspect\inventory.db` |
| Linux | `~/.local/share/io.github.kk4oda.cominspect/inventory.db` |
| macOS | `~/Library/Application Support/io.github.kk4oda.cominspect/inventory.db` |

The database runs in WAL mode with `synchronous=NORMAL` and foreign keys enabled.

```sql
-- Schema version lives in PRAGMA user_version.
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
  -- compat_schema: lowest schema an app must understand to WRITE this DB
  -- created_at, created_by_version, last_app_version, launch_pending_version, last_good_version

CREATE TABLE devices (
  id               INTEGER PRIMARY KEY,
  uuid             TEXT NOT NULL UNIQUE,        -- stable ID used by export/import
  -- user-assigned logical identity
  nickname TEXT, equipment TEXT, category TEXT, purpose TEXT,
  cat_status       TEXT NOT NULL DEFAULT 'unknown',  -- verified | not_cat | unknown
  notes TEXT,
  ignored          INTEGER NOT NULL DEFAULT 0,  -- user hid it from the main list
  -- hardware summary (latest observation)
  transport TEXT NOT NULL, vid INTEGER, pid INTEGER, serial_number TEXT,
  interface_number INTEGER, manufacturer TEXT, product TEXT, description TEXT,
  bt_address TEXT, virtual_provider TEXT,
  last_snapshot    TEXT,                        -- JSON DiscoveredPort for offline inspection
  -- machine-specific state
  last_port TEXT, connected INTEGER NOT NULL DEFAULT 0,
  first_seen INTEGER NOT NULL,                  -- unix ms, first observation by the app
  last_seen INTEGER,                            -- unix ms, last observed *connected*
  last_observed INTEGER NOT NULL,               -- unix ms, last observed at all (incl. phantom)
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);

CREATE TABLE identity_keys (                    -- fingerprint; strong keys unique in practice
  device_id INTEGER NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
  kind TEXT NOT NULL, value TEXT NOT NULL, strength INTEGER NOT NULL,
  first_seen INTEGER NOT NULL, last_seen INTEGER NOT NULL,
  PRIMARY KEY (device_id, kind, value)
);
CREATE INDEX identity_keys_lookup ON identity_keys(kind, value);

CREATE TABLE port_assignments (                 -- machine-specific COM history
  device_id INTEGER NOT NULL REFERENCES devices(id) ON DELETE CASCADE,
  port_name TEXT NOT NULL,
  first_observed INTEGER NOT NULL, last_observed INTEGER NOT NULL,
  last_connected INTEGER,
  PRIMARY KEY (device_id, port_name)
);

CREATE TABLE events (                           -- arrival/removal/renumbering log, pruned
  id INTEGER PRIMARY KEY, ts INTEGER NOT NULL,
  device_id INTEGER REFERENCES devices(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,                           -- new_device | connected | disconnected | port_changed | merged | imported
  port_name TEXT, previous_port TEXT, detail TEXT
);
CREATE INDEX events_device ON events(device_id, ts);

CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- JSON values
```

### Migrations

* Migrations are numbered, forward-only Rust functions, each run inside one transaction.
* **Before any migration**, a consistent copy of the database is written with `VACUUM INTO` to
  `backups/inventory-schema<N>-<timestamp>.db`. The same mechanism backs up the database before
  every app update and import, and on request. The ten newest backups are kept.
* **Forward compatibility.** Additive migrations (a new nullable column or table) leave
  `compat_schema` unchanged, so an *older* app can keep using a database written by a newer one.
  Only breaking migrations raise `compat_schema`.
* **Newer, incompatible database.** If an older app finds a database with a schema newer than it
  supports and `compat_schema` above its own schema (e.g. after a rollback), it never
  down-migrates or writes to the file. It runs on a **temporary in-memory database**, shows a
  banner explaining why, and offers the pre-upgrade backup (Database backups → Restore).
  Discovery keeps working.
* **Damaged file.** If the file fails SQLite's integrity check, it is moved aside
  (`inventory.damaged-<timestamp>.db`), a fresh database is created and the UI says where the old
  file went.
* Users never need to delete their configuration to upgrade.

### Export format (`serial-port-inventory.json`)

Each device's data is split into the three categories required by the brief:

```jsonc
{
  "format": "cominspect-inventory", "format_version": 1,
  "exported_at": "2026-09-26T14:32:17Z", "app_version": "0.1.0",
  "source": { "os": "windows", "hostname": "SHACK-PC" },
  "devices": [{
    "uuid": "…",
    "identity":  { "nickname": "FTDX10 CAT Enhanced", "equipment": "Yaesu FTDX10",
                   "category": "radio_cat", "purpose": "cat", "cat_status": "verified",
                   "notes": "Use for OmniRig" },                       // user-assigned, portable
    "hardware":  { "transport": "usb", "vid": "10C4", "pid": "EA70", "serial": "01A2B3C4",
                   "interface": 0, "product": "CP2105 Dual USB to UART Bridge Controller",
                   "keys": [{ "kind": "usb-serial", "value": "10C4:EA70:01A2B3C4:if0",
                              "strength": 100, "portable": true }, …] },  // device identity
    "machine":   { "last_port": "COM7", "port_history": ["COM5", "COM7"],
                   "first_seen": "…", "last_seen": "…" }                 // this PC only
  }]
}
```

Import works as follows:

* Devices are matched by UUID first, then by *portable* keys.
* The user chooses to **merge** (fill empty fields only) or **overwrite**.
* Identities not yet seen on the new machine are stored as *awaiting device* records. Their
  portable keys ensure that the radio is recognized, with its nickname, the first time it is
  plugged in, **whatever COM number that machine assigns**.
* Machine-specific history from another computer is kept for reference only. It is never applied
  as this machine's port assignment.

## 9. Update and release architecture

### Mechanism: Tauri updater plugin (not a custom updater)

* **Signing.** Every updater artifact is signed with an Ed25519/minisign key; Tauri refuses to
  install unsigned or mis-signed updates, and this cannot be disabled.
  * The public key is embedded in `tauri.conf.json`.
  * The private key lives only in the GitHub Actions secrets `TAURI_SIGNING_PRIVATE_KEY` and
    `…_PASSWORD`.
  * The app sets `requireSignedVersion: true`. This rejects a feed that pairs a new version
    number with an older, validly signed artifact (downgrade attack), and is possible because
    this project has no legacy unsigned releases.
* **Integrity chain:**
  1. HTTPS feed
  2. Download
  3. Minisign signature check
  4. Signed-version check
  5. Install
  6. Restart
  7. **Launch confirmation** (below)
* **Feed.** A static `latest.json`, generated and uploaded to each GitHub Release by
  `tauri-action`, keyed per platform/installer: `windows-x86_64-nsis`, `darwin-aarch64-app`,
  `linux-x86_64-appimage`, `linux-x86_64-deb`, …
* **Install per platform:**

  | Platform | Update artifact | Install behavior |
  |---|---|---|
  | Windows | NSIS installer, per-user (`%LOCALAPPDATA%`, no UAC prompt) | Runs in `passive` mode (progress bar only) and relaunches the app automatically |
  | macOS | `.app.tar.gz` | Replaced in place, then relaunched |
  | Linux | AppImage | Replaced in place |
  | Linux | `.deb` / `.rpm` | Installed through `pkexec` (graphical authentication prompt) |

* **Never touches user data.** The database, backups, settings and logs live in the per-user
  data directory, not the install directory. The NSIS uninstaller leaves app data in place
  unless the user explicitly ticks "delete application data".

### Channels

| Channel | Feed | Who gets it |
|---|---|---|
| Stable (default; the channel selector is tucked away under About & updates → Advanced) | `https://github.com/KK4ODA/ComInspect/releases/latest/download/latest.json` — GitHub's "latest" excludes prereleases and drafts | Everyone |
| Beta | `…/releases/download/updater-feeds/beta.json` (checked first) plus the stable feed. The release workflow copies each release's `latest.json` there when it is newer than the current one, so beta users also move on to newer stable releases | Only users who explicitly opt in |
| Nightly | Same mechanism, `nightly.json` | Architected, not published in v1 |

The channel is a stored setting that only the user can change, and endpoints are set at runtime
with `updater_builder().endpoints(…)`. Nothing ever moves a user to a beta silently.

### In-app behavior

* Five seconds after startup, and then whenever the last check is more than 20 hours old
  (evaluated hourly while running), a background task checks the feed. It never blocks startup, and failures are silent (logged only). The check can be
  turned off in About / Updates. No telemetry is sent; the only request is an HTTPS GET of a
  static JSON file.
* When an update is available, a subtle dot appears on the menu button, plus a status-bar item.
  **About / Updates** shows the installed version, the available version, the release date, notes
  and **Download and Install Update**, with a progress bar. "You're up to date." is shown when
  there is nothing new.
* **Launch confirmation and recovery.**
  * At startup the app records `launch_pending_version`. Once the UI reports that it has rendered
    the first inventory, it records `last_good_version`.
  * If a new version's previous launch never confirmed, the app shows a recovery banner with
    links to the logs and to **Reinstall previous version**.
  * The reinstall uses the previous release's own signed `latest.json` (every release carries
    one) with an explicit, user-initiated version comparator. The rollback therefore goes through
    the same signature verification.
  * Combined with the pre-migration database backups and the temporary-database mode for newer
    schemas ([§7](#migrations)), a failed update is recoverable without deleting anything.
* **Post-update notice.** On the first launch of a new version the app shows a toast,
  "Updated to 1.3.0", and records the update in the database.

### Release pipeline (GitHub Actions)

```
git tag v1.3.0 && git push origin v1.3.0
  └─► release.yml
       1. prepare: tag == Cargo/package version; update key configured;
          CHANGELOG.md section → release notes; create a *draft* release
       2. build matrix: unit tests, then tauri-action builds and uploads
          windows-latest (x64 NSIS + MSI), macos-latest (aarch64 and x86_64),
          ubuntu-22.04 (AppImage, deb, rpm), ubuntu-22.04-arm (optional)
          ├─ updater artifacts signed with TAURI_SIGNING_PRIVATE_KEY
          ├─ Windows Authenticode signing if certificate secrets are configured
          └─ macOS Developer ID + notarization if Apple secrets are configured,
             ad-hoc signature otherwise
       3. latest.json (one signed entry per platform and per installer type)
          is uploaded to the draft
       4. publish: scripts/check-updater-manifest.mjs verifies latest.json,
          then the release is un-drafted (so releases/latest/download/latest.json
          never points at a half-uploaded release)
       5. every release refreshes updater-feeds/beta.json when it is newer
```

Installations from a package (`.msi`, `.deb`, `.rpm`) can only be updated with a package of the
same kind (the updater looks up `{os}-{arch}-{installer}` first). If a release lacks one, the app
says so and links to the download page, instead of downloading an artifact it cannot install.
The manifest check warns about such gaps at release time.

`ci.yml` runs on every push and pull request, with the Rust version pinned in
`rust-toolchain.toml` so that a new Rust release cannot break the build by itself:

* `cargo fmt --check` and `clippy -D warnings`
* Unit tests on Windows, macOS and Linux
* Frontend type-check and tests
* A **smoke run of `cominspect-cli list --json`** on each OS, which exercises the real FFI paths
  on real Windows and macOS runners

Code signing (Authenticode, Apple Developer ID) is optional, driven by secrets. Unsigned builds
still update securely, because update integrity rests on the minisign signature, not on OS code
signing. Signing only removes SmartScreen and Gatekeeper warnings.

## 10. Major technical risks

| # | Risk | Mitigation |
|---|---|---|
| 1 | Windows and macOS FFI can't be run on the Linux dev machine | Collection/interpretation split, with fixture tests of interpretation; CI builds, tests and smoke-runs on real Windows and macOS runners; defensive FFI (bounded buffers, every call's error handled, no panics across FFI) |
| 2 | Property availability for phantom devnodes varies (parent/location may be absent) | Graceful degradation: the instance ID alone still identifies phantoms; USB details are learned while the device is present |
| 3 | Non-unique or missing USB serials (CH340, PL2303, clones, CP210x `0001`) | Serial hygiene rules, location-based keys, duplicate detection, user **Same device as…** merge, and a transparent "recognized by …" display |
| 4 | Opening a serial port can assert **DTR/RTS**, and many stations wire those to **PTT/CW keying** | No automatic port opening, ever. Diagnostics are user-initiated with an explicit warning; the PTT test needs a second confirmation and is time-limited; the CAT query sends only read-only commands chosen by the user |
| 5 | Non-PnP virtual-port drivers vary widely | SERIALCOMM catches all of them; provider names are heuristic and labelled as such |
| 6 | WebView availability: WebView2 on older Windows 10, WebKitGTK on Linux (webkit2gtk-4.1 needs Ubuntu 22.04+/Debian 12+) | The NSIS installer bootstraps WebView2; Linux requirements are documented; the CLI works without a GUI |
| 7 | Code-signing cost and reputation (SmartScreen, Gatekeeper) | Optional signing hooks in CI; documented first-run steps for unsigned builds |
| 8 | Loss of the updater private key would strand users | Documented key backup; runtime `pubkey` override enables key rotation in a future release |
| 9 | Database corruption (power loss) or bad migration | SQLite WAL, transactional migrations, pre-migration backups, damaged files moved aside, a temporary-database fallback, and JSON export |
| 10 | ModemManager on Linux probes new `ttyACM` devices; counterfeit Prolific chips on Windows | Surfaced as warnings/hints (Code 10 on PL2303 explained) |
| 11 | Future COM-number reassignment could corrupt the ComDB if done wrong | Deferred; architected around the supported `ComDBClaimPort`/`ComDBReleasePort` + `PortName` + friendly-name update path, requiring elevation and a restore point (see [§11](#11-mvp-scope)) |

## 12. Which program has a port open (v0.2)

A busy port is a common problem in a station: only one program can open it, and some programs hold
it for a while after they close (VARA FM can keep a Digirig's port for up to a minute, so VarAC
can't open it yet). Operators need to know *which* program has the port and *when* it lets go.

Opening the port to find out is not an option. It can key a transmitter through RTS or DTR, and it
races with the program that is about to use the port. ComInspect therefore reads usage from the
operating system and never opens the port for it (`cominspect-platform/src/usage/`).

| OS | Mechanism |
|---|---|
| Windows | `QueryDosDevice("COM4")` names the device behind the port (`\Device\Silabser0`). `NtQuerySystemInformation(SystemExtendedHandleInformation)` lists every open handle. File handles with read or write access, in processes the user may inspect, are duplicated into ComInspect and named with `NtQueryObject(ObjectNameInformation)`. A handle named like the device belongs to a program using the port. Duplicating a handle doesn't call the serial driver, so the port's lines never change. |
| Linux | The `/proc/<pid>/fd/*` links, compared with the port's canonical path |
| macOS | `libproc`: `proc_pidinfo(PROC_PIDLISTFDS)` and `proc_pidfdinfo(PROC_PIDFDVNODEPATHINFO)`, matching both the `/dev/cu.*` and `/dev/tty.*` names of a port |

On Windows, getting the answer right needs care:

- **Stalled name queries.** Naming a handle that was opened for synchronous I/O waits while another
  thread of its program is inside synchronous I/O on it (a blocked pipe read, for example), possibly
  forever. Queries therefore run on a worker thread. After 100 ms, the duplicate is closed at once
  so that ComInspect never keeps anyone's port open, a new worker continues, and the late answer is
  used by a later check. At most 64 workers may be stuck at a time.
- **Handle reuse.** A closed handle's value, and even its kernel object address, is often reused by
  the next file the program opens. Answers are cached per handle for 10 to 19 checks, but the
  handles that named a port are read again at every check.
- **Releases.** Before a port is reported free, its previous holders are read again without the
  cache. If a holder opened a handle after it was last seen with the port, and that handle's name
  can't be read yet, it may have reopened the port; the port stays "in use" for up to 15 s. Handles
  the holder already had while it held the port don't count, because a port can be open only once.
- **Programs shutting down.** Windows removes a handle from the table before the driver has finished
  closing it (pending USB I/O can take a while). A previous holder that is exiting (it has an exit
  code but still has handles) therefore keeps the port until it is done. The UI shows it as
  *shutting down*.
- **Visibility.** Without elevation, processes running elevated or as another user can't be
  inspected. The UI says so.

A real COM port in CI (`COMINSPECT_TEST_PORT=COM2` on the Windows runner) covers detection, release,
handle reuse, immediate reopening and a blocked synchronous read. A cross-process smoke test holds a
port from PowerShell (Windows) or Python (Linux, macOS) and checks `cominspect-cli who` and
`wait-free`.

**In the app** (`src-tauri/src/usage.rs`), a background thread checks the connected ports every
2 s while the window is visible and every 1 s while someone waits for a port, and never otherwise.
It emits `usage://updated`. When a watched port is free, it shows a notification
(tauri-plugin-notification) and starts the chosen program: `ShellExecuteW` on Windows, so that
shortcuts work, with the program's own folder as the working directory. The program is remembered
per device in the settings table (`usage.program.<device id>`), and closing the window while waiting
asks first. **The CLI** commands `who` and `wait-free` use the same probe.

## 13. VSPE links (v0.3)

Eterlogic VSPE connects ports: a Splitter shares one port through up to eight virtual ports, a Pair
joins two virtual ports, and user-mode devices (Redirector, TCP server and client, UDP) move data
between ports and the network. None of this is visible in the device tree, so ComInspect reads
VSPE's configuration (`cominspect-core/src/vspe.rs`).

**Why the file and not the VSPE API.** VSPE publishes an API (`VSPE_API.dll`, or a COM server) with
`vspe_getDeviceInfo`. It needs an activation key (free only for 32-bit), and it can't run while
VSPE's own service does: using it would mean stopping the user's VSPE. The configuration file
needs neither.

**Where.** VSPE 1.5 and later run a service (*Eterlogic Virtual Serial Ports emulator service*)
that loads `%ProgramData%\Eterlogic\VSPE\autostart.vspe` at startup. The app reads that file, or
one the user chose (stored in the `vspe.file` setting), again whenever its window becomes active.

**Format.** After a header with the 32-bit little-endian value `0x11223344` at offset 4, each
device is a record: the device type (`Splitter`) and its settings string, each a 32-bit length
followed by the bytes. VSPE 1.5.1 added titles, descriptions and a started/stopped state around the
records, so they are found by shape (a known type name followed by printable settings) rather than
at fixed offsets. Settings strings follow Eterlogic's *Devices initialization* page (for example
`10;9;0;19200,0,8,1,0,0;0;0;0`: a Splitter sharing COM9 as COM10), except for VSPE 1.5's
multi-port Splitter, `v2;<source>;<options>;<serial settings>;<count>;<port>;…`, where every virtual
port has the same number of fields and starts with its number. Other versioned formats (`v3;…`, or a
`v2` for other devices) are kept but not interpreted, so a future format can't produce wrong links.
A real configuration saved by VSPE 1.5 is a test fixture.

**Display.** The UI nests a Splitter's virtual ports under the port they share when both are in the
list (`ui/src/lib/vspe.ts`). Only virtual ports are nested, the connected device wins when several
devices had the source port's name, and chained splitters stay flat. Ports from known virtual-port
software count as virtual whatever bus Windows lists them on, since VSPE's ports sit on its own bus.
